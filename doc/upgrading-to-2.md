# Upgrading to 2.0

2.0 changes where Minepanel keeps things: server configuration on disk, proxy
settings in the database, and the mc-router container itself. Nothing is deleted,
and the upgrade runs on its own the first time the panel starts.

```bash
docker compose pull
docker compose up -d
```

## What happens on first start

**Each server gets a `server.json`.** Until now a server's configuration was
re-derived by parsing its `docker-compose.yml` on every read. On the first start,
2.0 parses every server's compose file once, writes the result to
`servers/<id>/server.json`, and never parses it again. A `servers/servers.json`
index is written alongside them so listing servers no longer opens all of them.

The migration runs at startup and logs what it did. A server whose compose file
cannot be parsed is **skipped and left exactly as it was** — no `server.json` is
written for it, so nothing is lost and it can be fixed by hand and picked up on the
next start. Check the backend log for `Could not migrate` if a server disappears
from the dashboard.

**Proxy and network settings move to the instance.** `proxyEnabled`,
`proxyBaseDomain`, `publicIp`, `lanIp` and the Java server defaults used to live in
one user's preferences even though they decide how every server's compose file is
generated. They are lifted into instance-wide settings once, taken from the oldest
user account.

Nothing is removed: `docker-compose.yml` stays in place for every server, so
rolling back to 1.11 works. You lose only the changes made while on 2.0.

## What you have to do yourself

### Remove the old mc-router container

The panel now generates and runs mc-router as its own compose project. The
`mc-router` service and its `proxy` profile are gone from the shipped compose
files, but a container started by the old one keeps running and would fight over
port 25565. Remove it once:

```bash
docker compose --profile proxy down
```

The panel never stops a router it did not create, so this step is yours.

### Move MC_PROXY_* out of .env

These variables are no longer read:

| Removed from `.env` | Now in |
| --- | --- |
| `MC_PROXY_PORT` | Settings → Network → Router port |
| `MC_PROXY_AUTOSCALE` | Settings → Network → Auto-scaling |
| `MC_PROXY_AUTOSCALE_TOKEN` | Generated by the panel, stored encrypted |
| `MC_PROXY_AUTOSCALE_DOWN_AFTER` | Settings → Network → Stop after |
| `MC_PROXY_AUTOSCALE_WAKE_TIMEOUT` | Fixed at 180s |
| `MC_PROXY_AUTOSCALE_ASLEEP_MOTD` | Settings → Network |
| `MC_PROXY_AUTOSCALE_LOADING_MOTD` | Settings → Network |

You do not have to generate a token any more. Turning auto-scaling on mints one.

### Networks you added by hand

If you edited the router's compose to attach an extra network, add it under
**Settings → Network → Extra Docker networks** instead. The generated file
overwrites hand edits.

## Editing compose files by hand is no longer supported

`servers/<id>/docker-compose.yml` is now generated output and carries a header
saying so. It is rebuilt from `server.json` every time a server starts or
restarts, so hand edits are discarded the moment the server runs. Edit
`server.json` instead, or use the fields that already exist for this: custom
environment variables, Docker labels, extra volumes and extra ports.

Editing `server.json` directly works: the change takes effect on the next start,
without touching the UI.

One thing this buys you: when a panel update changes how compose files are
generated, servers pick it up on their next start. Earlier versions kept the old
file until someone pressed save or ran "regenerate all".

## Behaviour that changed

**Settings that used to be silently lost now survive.** `spawnProtection`, the
Bedrock seed and game mode, and custom environment values containing `=` were
dropped or mangled when a server was saved. They round-trip correctly now, but
values already lost cannot be recovered — check those fields on servers that used
them.

**Proxy routing is instance-wide.** It never depended on who was asking, but it
was stored per user. If two admins had different proxy settings, the oldest
account's values win.

## Settings that stay in .env

Not everything moved. These are read before the database exists, or define where
it lives, so they stay environment variables: `JWT_SECRET`, `FRONTEND_URL`,
`BASE_DIR`, `BASE_PATH`, `COMPOSE_PROJECT` and `BACKUP_BASE_DIR`. SMTP and OIDC
still work from `.env` as a fallback, with the panel's values taking precedence.

## If something goes wrong

`servers/servers.json` is a cache. Deleting it is safe; the panel rebuilds it from
the folders on the next request.

To go back to 1.11, pin the previous tag. Every server still has its
`docker-compose.yml`, which is what 1.11 reads:

```bash
docker compose down
# pin the previous version in your compose file, then
docker compose up -d
```
